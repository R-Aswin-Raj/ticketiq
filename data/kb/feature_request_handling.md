# Feature Request Handling

## What to do with a feature request
1. Thank the customer and confirm the specific outcome they want, not just the feature they named.
2. Check whether an existing capability or workaround already covers it.
3. Log the request against the account so product can weight demand by revenue and tier.
4. Never promise a delivery date. The correct language is that the request has been recorded
   and shared with the product team.

## Known roadmap status
- **Dark mode** — in design, no committed date.
- **Scheduled report delivery** — planned for the next quarter; a workaround exists using the
  export API plus a cron job.
- **Bulk editing** — under evaluation, gated on the new permissions model.
- **Slack notifications** — available today via outbound webhooks; a native app is not planned.
- **Custom fields** — available on enterprise plans only.
- **Granular roles** — enterprise only; pro plans have admin/member roles only.

## Tier handling
Enterprise requests are routed to the assigned account manager with a summary. Free and pro
requests are aggregated and reviewed monthly. Never tell a free-tier customer their request is
lower priority; say it is recorded and reviewed with all other input.
